# AIコーディングの次の課題: 速度ではなく、仕様・検証・責任を設計せよ

AIコーディングを導入した現場では、「実装は速くなったのに、なぜか開発全体は楽にならない」という違和感が起きている。コードを書く摩擦は下がった一方で、レビュー、QA、運用、育成、セキュリティの負荷はむしろ目立つようになった。これはAIが役に立たないという話ではない。AIコーディングの本質が、コード生成速度の向上ではなく、仕様・検証・責任の設計を組織能力にすることへ移ったという話である。

## AIで開発は速くなった。しかし、なぜ現場は楽にならないのか

AIが速くした工程は明確だ。ボイラープレート、既存コードに沿った小さな変更、テストケース案、ドキュメント草案、エラーメッセージの読み解きは、以前より短時間で進められる。個人が「最初のPRを作る」までの時間は短くなりやすい。

しかし、組織が価値を届ける速度は、実装開始の速度だけでは決まらない。仕様が妥当か、既存設計と矛盾しないか、テストは重要な失敗モードを押さえているか、リリース後に誰が説明できるかを確認する工程は残る。むしろ生成量が増えるほど、人間が読むべき差分、判断すべき設計、確認すべき運用リスクは増える。

この構造を、この記事では「速度の前払い」と「認知負債の後払い」と呼ぶ。AIは早い段階で成果物らしきものを出すことで速度を前払いする。一方で、そのコードを理解し、統合し、検証し、説明する負荷は後工程に請求される。資料でも、AI導入による速度向上とレビュー・品質負荷の増大が併せて論じられているが、調査条件や測定対象は資料ごとに異なるため、数値を単純に横比較するべきではない[1][2]。重要なのは、個人の実装速度と組織の完了速度を分けて見ることだ。

## Vibe Codingの限界と、後工程に押し寄せる負荷

Vibe Codingは、曖昧な自然文でAIに意図を伝え、対話しながら動くものを作る実践として広がった。探索、プロトタイピング、個人の学習では有効な場面がある。しかし、チームで保守する本番コードでは限界が早く現れる。

問題は、AIが生成したコードが「動いているように見える」ことと、「組織が意図した仕様を満たしている」ことが別である点にある。仕様が曖昧なまま実装されたコードは、レビュー時に正誤を判定しにくい。レビュアーは差分を読むだけでなく、暗黙の要件、非機能要件、既存設計、過去の障害対策まで頭の中で再構築しなければならない。QAは、実装後に仕様を推測しながらテスト観点を作ることになる。運用担当は、意図が説明されていない挙動を監視・障害対応の対象にする。若手は、コードを書く過程で得られる失敗やデバッグの経験を飛ばし、生成物だけを受け取ってしまう。

ここで押し寄せる負荷は、単なる技術的負債ではない。初出なので用語を整理しておく。

- **認知負債**: チームがシステムを理解する力を十分に形成しないまま、成果物だけが増える状態。
- **理解負債**: 個々の開発者が、自分が採用したコードの挙動や影響範囲を説明できない状態。認知負債の個人側の症状として現れる。
- **意図負債**: なぜその設計・例外・制約が必要なのかという背景がコードやテストから失われる状態。

AI時代の怖さは、これらの負債が高速に積み上がることにある。AIが実装とテストを同時に生成すると、CIは通っているのに、何の仕様を保証しているのか分からないテストが増える。これは「仕様なき検証」である。テストがあること自体は良い。しかし、人間が先に受け入れ条件や失敗モードを決めていなければ、テストは仕様の検証ではなく、生成物に合わせた自己正当化になりうる[3][4]。

## AI時代に壊れる4つの前提

### 前提1: コードは人間が書く量だけ増える

従来のレビューやQAは、人間が書ける量を暗黙の上限としていた。AIはこの上限を外す。実装者は短時間で大きな差分を作れるが、レビュアーの読解速度、QAの設計速度、運用担当のリスク評価速度は同じ比率では上がらない。

その結果、AIが速くした工程と遅くした工程が分かれる。実装開始、たたき台作成、単純な修正は速くなる。一方で、レビュー待ち、意図確認、手戻り、障害時の原因調査、若手への説明は遅くなりやすい。PR数やコード行数をAI導入のKPIにすると、この負荷移動を見落とす。見るべき指標は、リードタイム、レビュー滞留、欠陥流出、手戻り率、オンボーディング後の説明力である。

### 前提2: 実装者はコードの意図を説明できる

人間が手で書いたコードであっても、常に意図を説明できるとは限らない。ただ、試行錯誤、デバッグ、設計判断の過程を経ることで、一定の理解は形成されやすかった。AI生成コードでは、この過程を省略できてしまう。

したがってレビューの問いは、「このコードは動くか」だけでは足りない。「なぜこの設計なのか」「どの代替案を捨てたのか」「どの仕様を満たし、どのリスクを受け入れたのか」「障害時に誰が説明するのか」を問う必要がある。AIを使ったかどうかではなく、採用した出力を所有できるかがレビュー対象になる。

### 前提3: AIは将来の保守負担を自然には最小化しない

人間のエンジニアには、将来の作業を減らすために重複を避け、単純な設計を選び、不要なコードを削る動機がある。資料ではこれを、プログラマーの美徳としての「怠惰」と関連付けて論じている[5]。ここでいう怠惰は手抜きではなく、将来の保守負荷を減らすための知的努力である。

AIには、コードが増える痛みがない。制約を与えなければ、似たような関数、場当たり的なテスト、用途不明なヘルパー、過剰な抽象化を生成しやすい。こうした低品質な生成物は、しばしば **AI slop** と呼ばれる。AI slopは、動作しているように見えるため発見が遅れ、あとから保守性、変更容易性、レビュー可能性を下げる。

### 前提4: ツールは人間の補助であり、権限境界は明確である

AIエージェントは、補完ツールではなく実行主体に近づいている。ファイルを書き換え、コマンドを実行し、外部APIを呼び、場合によってはデプロイやインフラ操作に触れる。ここでは便利さと同時に、権限過多、プロンプトインジェクション、秘密情報の読み取り、監査不能な変更というリスクが生じる[6][7]。

従来は「人間が操作するから権限境界は人間の判断で守られる」と考えられた。しかしエージェント化が進むほど、権限境界は仕組みとして明示しなければならない。AIを信頼するかどうかではなく、信頼しなくても安全に止まる設計が必要になる。

## 会話の巧さではなく、仕組みでAIを使う

AIコーディングを組織能力にするには、プロンプトが上手い人を増やすだけでは不十分だ。必要なのは、AIがよい出力を出しやすく、悪い出力が後工程に流れにくい仕組みである。

### 1. 仕様駆動でAIの出力空間を狭める

仕様駆動開発は、重い設計書を復活させる話ではない。AIが間違った自由度を持たないように、出力空間を狭める制御面を作ることだ[8]。最低限、AIに実装を依頼する前に次を明文化する。

| 項目 | 書くべきこと |
| :--- | :--- |
| 目的 | 何の業務価値、ユーザー価値、運用上の問題を解くのか |
| スコープ / 非スコープ | 変更してよい範囲と、触ってはいけない範囲 |
| 受け入れ条件 | 何が満たされれば完了と言えるのか |
| 失敗モード | 例外、境界値、権限不足、外部サービス障害をどう扱うか |
| 設計制約 | 既存アーキテクチャ、命名、依存方向、互換性 |
| 検証観点 | 単体、結合、E2E、手動確認、監視で何を確認するか |
| 責任者 | 仕様判断、レビュー、リリース判断、運用説明を誰が持つか |

この表は、AIへの入力であると同時に、レビューとQAの基準でもある。仕様があれば、AIが生成したテストが仕様を検証しているかを確認できる。仕様がなければ、レビューは「雰囲気の正しさ」を読む作業になってしまう。

### 2. レビューを設計判断の検証へ移す

AI時代のレビューは、全行を同じ重さで読む作業から、検証の階層化へ移る。Lint、型検査、静的解析、依存関係チェック、セキュリティスキャン、自動テストは前段のハーネスにする。人間は、そこでは拾いにくい設計判断、仕様妥当性、責任分界、運用影響を見る。

| 従来のレビュー観点 | AI時代のレビュー観点 |
| :--- | :--- |
| コードが読めるか | 仕様に対して必要十分か |
| バグがなさそうか | 想定した失敗モードを検証しているか |
| スタイルが合っているか | 既存設計と責任分界に合っているか |
| 実装者が書いたか | 実装者が説明し、所有できるか |
| テストがあるか | テストが人間の意図を保証しているか |

レビューで見るべき最重要ポイントは、「AIが何を出したか」ではなく「チームが何を保証すると決めたか」である。

### 3. TDD、体系的デバッグ、段階的実行をAIに強制する

AIに「作って」と頼むだけでは、近道を選びやすい。テストを後回しにする、原因を特定せずに修正する、大きな変更を一度に入れる、検証前に完了を宣言する。これを防ぐには、会話ではなく手順で縛る。

SuperpowersやSkillsのような仕組みは、特定ツールの優劣ではなく、開発規律をAIに守らせる具体例として捉えるとよい[9]。たとえば次のルールを、社内テンプレート、CI、レビュー基準、エージェント設定に落とし込む。

- 失敗するテスト、または人間が承認した検証観点がない限り、実装を始めない。
- 根本原因を特定するまで修正コードを書かない。
- 大きな変更は、小さな計画と承認単位に分ける。
- 変更後は、実行した検証、未検証事項、残リスクを必ず報告する。
- AIが生成したテストについて、「どの仕様を保証するか」を説明させる。

TDDも体系的デバッグも、AIに任せるための儀式ではない。人間の意図をコードと検証に接続し続けるためのプロトコルである。

### 4. エージェントには最小権限と承認ゲートを設ける

エージェント運用では、開発体験を優先して権限設計を後回しにしてはいけない。最小権限、承認ゲート、監査を最初から設計する。

| ガードレール | 実務での設定例 |
| :--- | :--- |
| 最小権限 | リポジトリ、ディレクトリ、コマンド、外部通信先をタスク単位で限定する |
| 承認ゲート | ファイル削除、依存追加、外部送信、デプロイ、インフラ変更は人間承認にする |
| シークレット隔離 | `.env`、本番認証情報、顧客データをエージェントの読み取り対象から外す |
| 監査ログ | 参照ファイル、実行コマンド、生成物、承認者、却下理由を残す |
| サンドボックス | 本番環境と切り離した限定環境で実行し、ネットワークも必要最小限にする |

「AIが賢いから大丈夫」ではなく、「AIが誤っても被害が限定され、後から追跡できる」ことが統制の条件である。

### 5. 若手育成ではAI利用と説明責任をセットにする

若手にAIを禁止するだけでは、現実の開発環境から切り離された訓練になる。一方で、AI出力の丸写しを許すと、理解負債が増える。育成で設計すべきなのは、AI利用の有無ではなく説明責任である。

具体的には、次のような課題に変える。

- AIに依頼する前に、自分の設計仮説を短く書く。
- AI出力の危険箇所、過剰実装、テスト不足を指摘する。
- 生成コードの挙動と設計意図を自分の言葉で説明する。
- AI案と自分の案を比較し、採用・不採用の理由を述べる。
- 障害を想定し、どこから調査するかを説明する。

AIを「答えを出す道具」ではなく、「自分の理解を検査する相手」として使わせる。これにより、AIを使いながらデバッグ力、設計判断、所有権を育てられる。

## 結論: AI時代のエンジニアリングは、生成ではなく所有の競争になる

AIコーディングの成熟度は、どれだけ多くのコードを生成できるかでは測れない。重要なのは、何を作るべきかを仕様として定義し、AIの出力を検証し、設計判断を説明し、最終的な責任を持てる組織能力である。

コードを書く主体がAIに近づくほど、人間の価値は上流と下流に移る。上流では、問題設定、仕様化、制約設計を担う。下流では、検証、説明、運用、監査、育成を担う。つまり、AI時代のエンジニアリングは生成の競争ではなく、所有の競争になる。

明日から着手するなら、次の5つでよい。

1. AI導入KPIを、生成量ではなくレビュー滞留、欠陥流出、リードタイム、手戻り、学習効果で見直す。
2. AIに依頼する前の最小仕様テンプレートをチームで作る。
3. 生成テストに対して「どの仕様を保証するか」をレビュー項目に入れる。
4. エージェントの権限、承認ゲート、シークレット隔離、監査ログを標準化する。
5. 若手の評価を、AI使用可否ではなく、説明責任、代替案比較、デバッグ方針で見る。

AIコーディングの本質は、速く書くことではない。速く生成されるものを、組織として安全に受け止め、検証し、所有できるようにすることだ。
